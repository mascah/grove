# Grove constitution

Draft 2026-10-14, amended 2026-10-15 and 2026-10-17. It is the only document
whose sentences bind an agent. `grove.md` is direction, the docs in `docs/` are
the spec, `dev/walkthrough.md` runs them on the fixture, this file is the law.
Every rule is one line and numbered so it can be quoted. Changing this file is
its own commit with no code in it, and the owner reads it before any code
follows.

Rules restate entries in `decisions.md`: 1 is D-33; 2 and 3 are D-13, D-21, D-39, D-48 and D-50; 4 and 5 are D-02 to D-04 and D-38; 6 is D-24; 7 is D-01 and D-06; 8 is D-40; 9 is D-15 and D-35; 10 is D-34 and D-43; 11 is D-23 and D-33; 23 is D-30; 24 is D-28; 22 is D-31; 27 is D-32, D-41, D-42 and D-49. The size rules 12 to 18 are new and become decisions when the owner adopts this file.

## Product boundaries

1. Grove prints instructions; the user's own agent, in a harness the user runs, follows them. Grove launches no process.
2. `instructions apply <change-id>` prints instructions and exits. Grove creates no workspace and launches no session to apply a change.
3. Implementation progress is a convention in `implementation.md`, written by the applying agent and read by people. `archive` reads it only to refuse a change unless every task in `tasks.md` has `Status: done` there, or the file says `Status: dropped`. Archive reconciles a finished change's specs into the maintained specs and moves the change to `changes/archive/`.
4. Approval is the proposal being in the target branch. It never means implemented. Merging, committing, saving or ending a session approves nothing.
5. Three meanings stay apart: maintained spec (agreed), change set (approved future work), observed behavior (evidence). Explore is a conversation and saves no document of its own. Code enforces the distinction only where a display or instruction would otherwise blur it.
6. Review is `review`, a readout of what merging the current branch would agree to. No manifests, provenance records or review document kind until GitHub review exists.
7. Markdown in Git, Git required, no service, no database, no index. Changes and specs are files under one configured root.
8. The user documentation in `docs/` is the specification; `dev/walkthrough.md` runs its steps on the fixture. A command, flag, field, message or file exists only if a documentation step needs it.
9. Thin skills generated by `init`, for each harness `grove.yaml` lists, run `<binary> instructions <workflow> ...` in the caller's session and follow the result. They never launch another agent.
10. The document set, templates and workflows are one schema held as data; instructions are built as one value before they are printed; harnesses are rows in a table. None is a user-facing option until the documentation names it. The schema is a plain list of document kinds, each with a path, template and guide, and of workflows; it holds no dependencies between steps and no status. It is not a workflow engine (D-23).
11. Out of scope until the owner writes them in here: session launching and resume, worktrees, cycles, completion, GitHub, tmux dashboard, launch profiles, project schemas, cleanup, autonomous execution.

## Size and shape

12. Budget: 5,000 non-test Go lines and 3,000 test lines, counted by `just check`, which fails above them. Raising the budget is a change to this file.
13. No guard or fallback for a state no documented step can reach, unless a failure was reproduced on the fixture and named in the commit message. Handling an error that a call returns is not a guard.
14. A user-facing message is one sentence. Explanation lives in the guides and the walkthrough, not in Go strings.
15. Each package has one job, stated in its package comment, and a new package is named in the message of the commit that adds it. No interface with one implementation, no converter between two structs that mean the same thing.
16. Dependencies are the standard library plus what the owner lists here: `gopkg.in/yaml.v3`, Bubble Tea, Glamour, `golang.org/x/term`. Nothing else without a change to this file.
17. End-to-end tests follow the walkthrough on real disposable Git repositories. Logic with branches, such as a parser or the schema loader, may also have a small direct test. No PTY harness, fake Git, or adversarial-input suite without a reproduced bug.
18. Comments say why, not what. A function whose name and body say what it does has no comment.

## How agents work here

19. Read this file first in every session and every sub-agent brief; quote the rule number for anything called fixed or out of scope.
20. Scope lives here and only here. `AGENTS.md` describes the code and points to this file; it never restates scope.
21. Questions about whether Grove should do something are asked in text, name the rule they would cross, and offer no recommended option. "How should it work" is asked only after "whether" is answered.
22. An owner's answer from a phone or a tap is a lean, not a decision. A decision is the owner's words written into `decisions.md` or this file.
23. Adversarial review is run by the owner, by hand, after a real run. Agents do not invoke it, and a finding gets a fix only with a fixture reproduction.
24. Harness behavior that varies by user settings, such as permission prompts, is never a design input.
25. Decisions in documents are the owner's, in the owner's words, attributed. Agent inference goes under open questions or assumptions to confirm.
26. One walkthrough step per commit, demonstrated on the fixture with the command in the message. No bundling a fix round into a feature commit.
27. `~/GitHub/mascah/grove-legacy`, `~/GitHub/mascah/grove` and `~/GitHub/mascah/bench` are read-only. Copied code is listed in `dev/reuse.md` with path and revision. The only remote is the owner's private GitHub repository. Agents add no hook and install nothing globally; the owner installs the everyday `grove`. The repository names no other tool as Grove's model or point of comparison.
