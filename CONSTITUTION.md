# Grove constitution

Draft 2026-10-14, amended 2026-10-15, 2026-10-17, 2026-10-19, 2026-10-20 and 2026-10-21. It
is the only file that says what Grove does and does not do, and what size and
shape its code keeps. The docs in `docs/` are the spec, `dev/walkthrough.md`
runs them on the fixture, this file is the law. Every rule is one line and
numbered so it can be quoted. Changing this file is its own pull request with no
code in it, and the owner reads it before any code follows. How agents work here
is in `CLAUDE.md`; how to build, test, commit and release is in
`CONTRIBUTING.md`.

## Product boundaries

1. Grove prints instructions; the user's own agent, in a harness the user runs, follows them. Grove launches no agent, except one session at a time from `run` (rule 2).
2. `instructions apply` prints instructions and exits. `run` launches one bounded session of the user's agent on the apply skill, in a checkout the user prepared, and waits for it. Grove creates no workspace.
3. Implementation progress is a convention in `implementation.md`, written by the applying agent and read by people. It is Grove's, not a schema's: every schema lists its tasks as `T-NN` headings in `tasks.md` and records their status in `implementation.md`. Grove reads them only to report each task's status in the project value; in `archive`, to refuse a change unless every task in `tasks.md` has `Status: done` there, or the file says `Status: dropped`; and in `instructions apply` and `check`, to tell a change archived as finished from a dropped one. Archive does the finishing work the change's schema describes and moves the change to `changes/archive/`.
4. Approval is the proposal being in the target branch. It never means implemented. Merging, committing, saving or ending a session approves nothing.
5. Three meanings stay apart: maintained spec (agreed), change set (approved future work), observed behavior (evidence). Explore is a conversation and saves no document of its own. Code enforces the distinction only where a display or instruction would otherwise blur it.
6. Review is `review`, a readout of what merging the current branch would agree to. No manifests, provenance records or review document kind until GitHub review exists.
7. Markdown in Git, Git required, no service, no database, no index. Changes and specs are files under one configured root. `run` keeps its lock, attempt records and output under the checkout's `.git/grove/`; they approve nothing and record no task's progress.
8. The user documentation in `docs/` is the specification; `dev/walkthrough.md` runs its steps on the fixture. A command, flag, field, message or file exists only if a documentation step needs it. Guides in `docs/guides/` are trialed recipes that use Grove's existing features; they are not specification.
9. Thin skills or commands generated by `init`, for each harness `grove.yaml` lists, run `<binary> instructions <skill> ...` in the caller's session and follow the result. They never launch another agent.
10. Grove's skills and the change schemas are held as data; instructions are built as one value before they are printed; harnesses are rows in a table. None is a user-facing option until the documentation names it. A schema is a plain list of document kinds, each with a path, template and guide, and of each skill's guide and the kinds it writes; it holds no dependencies between steps and no status. A project adds schemas and overrides the built-in one file at a time; it adds no skill and no gate. It is not a workflow engine (D-23).
11. Out of scope until the owner writes them in here: session resume, worktrees, cycles, Grove pushing to GitHub or any other tracker itself, tmux dashboard, launch profiles, cleanup, Grove scheduling an agent itself, recovering an interrupted run, runs on disposable runners, coordinating runs across hosts. A guide may have the user's own pipeline run the user's agent on Grove's skills; rules 1, 2 and 9 still hold there.

## Size and shape

12. Budget: 5,000 non-test Go lines and 3,000 test lines, counted by `just check`, which fails above them. Raising the budget is a change to this file.
13. No guard or fallback for a state no documented step can reach, unless a failure was reproduced on the fixture and named in the commit message. Handling an error that a call returns is not a guard.
14. A user-facing message is one sentence. Explanation lives in the guides and the walkthrough, not in Go strings.
15. Each package has one job, stated in its package comment, and a new package is named in the message of the commit that adds it. No interface with one implementation, no converter between two structs that mean the same thing.
16. The `grove` binary's dependencies are the standard library plus what the owner lists here: `gopkg.in/yaml.v3`, Bubble Tea, Glamour, `golang.org/x/term`. Nothing else without a change to this file. CI may use other tools, such as the docs site build and the release pipeline.
17. End-to-end tests follow the walkthrough on real disposable Git repositories. Logic with branches, such as a parser or the schema loader, may also have a small direct test. No PTY harness, fake Git, or adversarial-input suite without a reproduced bug.
18. Comments say why, not what. A function whose name and body say what it does has no comment.
