# Grove constitution

Draft 2026-10-14, amended 2026-10-15, 2026-10-17, 2026-10-19, 2026-10-20, 2026-10-21, 2026-10-22 and 2026-10-23. It
is the only file that says what Grove does and does not do, and what size and
shape its code keeps. The maintained specs in `grove/specs/` are the spec,
`docs/` explains them, `dev/walkthrough.md` runs the docs on the fixture, this
file is the law. Every rule is one line and
numbered so it can be quoted. Changing this file is its own pull request with no
code in it, and the owner reads it before any code follows. How agents work here
is in `CLAUDE.md`; how to build, test, commit and release is in
`CONTRIBUTING.md`.

## Product boundaries

1. Grove prints instructions; the user's own agent, in a harness the user runs, follows them. Grove launches no agent, except one session at a time from `run` (rule 2).
2. `instructions` prints instructions and exits. `run` launches one bounded session of the user's agent on the implement skill, with no owner in the session, for one cycle, the one it is given or else the oldest marked `unattended`, in a checkout the user prepared, and waits for it. Grove creates no workspace.
3. Implementation progress is a convention in `implementation.md`, written by the implementing agent and read by people. It is Grove's, not a schema's: every schema lists its tasks as `T-NN` headings in `tasks.md`, each naming the files it touches, and records their status in `implementation.md`. Grove reads them only to report each task's status in the project value; in `archive`, to refuse a change unless every task in `tasks.md` has `Status: done` there, or the file says `Status: dropped`; in `instructions implement`, `run` and `check`, to tell a change archived as finished from a dropped one; and in `check`, `instructions implement` and `run`, to tell a task whose named file changed on the target since the change's `base`, or since the `planned` commit of the cycle it is in. Archive does the finishing work the change's schema describes, refuses a finished change when the maintained specs do not hold its requirements as it gives them, or its fold altered a maintained requirement it does not name, and moves the change to `changes/archive/`.
4. Approval is the proposal being in the target branch. It never means implemented. Merging, committing, saving or ending a session approves nothing. A change revised on its branch by `implement`, with the owner's agreement, is approved as revised once the target holds it. A change drafted on the branch that implements it, with the owner in the session, is approved with its code by the merge that brings both into the target; `run` builds only changes the target already holds. A cycle is planned when its file is in the target branch; `unattended: true` there hands it to a `run` given no cycle, and approves nothing more; giving `run` a cycle approves nothing more either.
5. Three meanings stay apart: maintained spec (agreed), change set (approved future work), observed behavior (evidence). Explore is a conversation and saves no document of its own. Prototype saves no document of its own either: its throwaway code stays on a `prototype/<slug>` branch that is never merged into the target, and its findings reach the target only in a proposal. Code enforces the distinction only where a display or instruction would otherwise blur it.
6. Review is `review`, a readout of what merging the current branch would agree to. No manifests, provenance records or review document kind until GitHub review exists.
7. Markdown in Git, Git required, no service, no database, no index. Changes, specs and cycles are files under one configured root. `run` keeps its lock, attempt records and output under the checkout's `.git/grove/`; they approve nothing and record no task's progress.
8. The maintained specs in `grove/specs/` are the specification of what Grove does; the user documentation in `docs/` explains it in plain words and links the specs rather than restating their rules; `dev/walkthrough.md` runs the documentation's steps on the fixture. A command, flag, field, message or file exists only if a documentation step needs it. Guides in `docs/guides/` are trialed recipes that use Grove's existing features; they are not specification.
9. Thin skills or commands generated by `init`, for each harness `grove.yaml` lists, run `<binary> instructions <skill> ...` in the caller's session and follow the result. They never launch another agent.
10. Grove's skills and the change schemas are held as data; instructions are built as one value before they are printed; harnesses are rows in a table. None is a user-facing option until the documentation names it. A schema is a plain list of document kinds, each with a path, template and guide, and of each skill's guide and the kinds it writes; it holds no dependencies between steps and no status. A project adds schemas and overrides a built-in one file at a time; it adds no skill and no gate. Grove's own gates are these: a change waiting on its `depends_on`, archive's refusals (rule 3), and `run` building no cycle that is neither given to it nor marked `unattended`, that waits on a cycle its `depends_on` names that is not done, that has a change the owner said needs a human, or whose changes, or the files their tasks name, differ from what its plan checked other than by the merges that archived the changes of the cycles it depends on; beyond them Grove orders and blocks nothing and is not a workflow engine.
11. Out of scope until the owner writes them in here: session resume, worktrees, Grove pushing to GitHub or any other tracker itself, tmux dashboard, launch profiles, cleanup, Grove scheduling an agent itself, recovering an interrupted run, runs on disposable runners, coordinating runs across hosts. A guide may have the user's own pipeline run the user's agent on Grove's skills; rules 1, 2 and 9 still hold there.

## Size and shape

12. Budget: 5,000 non-test Go lines, 3,000 test lines, and 8,000 words of instruction text in `internal/instruct` (its Markdown and YAML files), counted by `just check`, which fails above them. Raising the budget is a change to this file.
13. No guard or fallback for a state no documented step can reach, unless a failure was reproduced on the fixture and named in the commit message. Handling an error that a call returns is not a guard.
14. A user-facing message is one sentence. Explanation lives in the guides and the walkthrough, not in Go strings.
15. Each package has one job, stated in its package comment, and a new package is named in the message of the commit that adds it. No interface with one implementation, no converter between two structs that mean the same thing.
16. The `grove` binary's dependencies are the standard library plus what the owner lists here: `gopkg.in/yaml.v3`, Bubble Tea, Glamour, Lip Gloss, `golang.org/x/term`. Nothing else without a change to this file. CI may use other tools, such as the docs site build and the release pipeline.
17. End-to-end tests follow the walkthrough on real disposable Git repositories. Logic with branches, such as a parser or the schema loader, may also have a small direct test. No PTY harness, fake Git, or adversarial-input suite without a reproduced bug. The skill trials in `dev/trials.md` may be run by a script under `dev/` that drives the user's agents headless on disposable fixtures, answering them from a script and having a model judge the counts.
18. Comments say why, not what. A function whose name and body say what it does has no comment.
